# ADR-003. Выбор технологии потоковой обработки событий

**Дата:** 2026-08-05

**Статус:** Создано

## Контекст

В текущей архитектуре AdScale сервис **Statistics Service** синхронно записывает информацию о показах и кликах непосредственно в общую базу данных PostgreSQL. Запись выполняется в рамках обработки пользовательского запроса и входит в критический путь (hot path).

При росте нагрузки операции записи начинают конкурировать с обработкой RTB-аукционов, финансовыми транзакциями и аналитическими запросами, что приводит к увеличению времени отклика системы и превышению целевого SLA.

Для достижения требуемой производительности необходимо исключить обработку статистики из критического пути и перейти к асинхронной обработке событий.

### Ключевые архитектурные драйверы

* Производительность: P95 ≤ 100 мс
* Масштабируемость: поддержка 18 000 RPS с перспективой роста до 50 000 RPS
* Высокая пропускная способность при обработке событий показов и кликов
* Надёжная доставка событий без их потери
* Возможность горизонтального масштабирования обработки событий
* Инкрементальное внедрение без остановки платформы

Рассматривались три альтернативы:

1. Оставить синхронную запись статистики.
2. Использовать RabbitMQ.
3. Использовать Apache Kafka.

### Альтернатива 1. Сохранить синхронную запись в PostgreSQL

**Плюсы:**

* отсутствуют изменения архитектуры;
* простая реализация;
* не требуется внедрение дополнительных компонентов.

**Минусы:**

* запись статистики остаётся частью критического пути;
* увеличивается нагрузка на PostgreSQL;
* невозможно эффективно масштабировать обработку событий;
* сохраняется риск превышения SLA при росте нагрузки.

### Альтернатива 2. Использовать RabbitMQ

**Плюсы:**

* позволяет реализовать асинхронную обработку;
* прост в эксплуатации;
* поддерживает различные модели доставки сообщений.

**Минусы:**

* менее эффективен при обработке очень больших потоков событий;
* ограниченные возможности долговременного хранения сообщений;
* менее удобен для повторной обработки событий и построения аналитических потоков.

### Альтернатива 3. Использовать Apache Kafka

**Плюсы:**

* высокая пропускная способность;
* горизонтальное масштабирование кластера;
* долговременное хранение событий;
* возможность повторного чтения сообщений;
* возможность подключения нескольких независимых потребителей;
* хорошо подходит для событийной архитектуры RTB-платформы.

**Минусы:**

* более сложное администрирование;
* необходимость сопровождения Kafka-кластера;
* увеличение сложности инфраструктуры.

## Решение

В качестве платформы потоковой обработки событий выбрана **Apache Kafka**.

Приняты следующие принципы реализации:

* Delivery Service публикует события показов и кликов в Kafka;
* Statistics Service асинхронно обрабатывает события и сохраняет их в специализированное хранилище;
* Analytics Service использует поток событий для формирования отчётности без обращения к production-нагрузке;
* критический путь обработки RTB-запросов не включает операции записи статистики;
* Kafka используется как единая шина событий для последующего развития событийной архитектуры платформы.

## Последствия

### Положительные

* запись статистики исключается из критического пути обработки RTB-запросов;
* уменьшается нагрузка на PostgreSQL;
* повышается производительность системы;
* появляется возможность независимо масштабировать обработку событий;
* создаётся основа для построения событийно-ориентированной архитектуры.

### Отрицательные

* увеличивается сложность инфраструктуры;
* требуется сопровождение Kafka-кластера;
* возрастает сложность мониторинга и эксплуатации системы.

### Риски

* при неправильной настройке Kafka возможно увеличение задержек доставки сообщений;
* необходимо обеспечить идемпотентную обработку событий для исключения ошибок при повторной доставке;
* отказ потребителей может привести к накоплению очередей сообщений и увеличению времени обработки статистики.
