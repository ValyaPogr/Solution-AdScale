# ADR-001. Стратегия эволюции архитектуры (от монолита к микросервисам)

**Дата:** 2026-08-05

**Статус:** Создано

## Контекст

Платформа AdScale должна обеспечить интеграцию с новой DSP-площадкой и увеличить производительность системы с текущих **15 000 RPS** до **18 000 RPS** без ухудшения SLA. В течение следующего года архитектура должна обеспечить возможность масштабирования до **50 000 RPS**.

Текущая архитектура представляет собой монолит с единой PostgreSQL, в которой одновременно выполняются транзакционные операции, запись статистики и аналитические запросы. Анализ AS-IS выявил превышение SLA (P95 = 110–120 мс при требовании ≤100 мс), отсутствие кэширования, очередей сообщений и независимого масштабирования наиболее нагруженных компонентов.

### Ключевые архитектурные драйверы

* Производительность: P95 ≤100 мс
* Масштабируемость: до 50 000 RPS
* Доступность: отсутствие простоя при миграции
* Надёжность: устранение Single Point of Failure
* Срок реализации: 3 месяца
* Ограниченный бюджет проекта
* Возможность дальнейшего развития платформы

Рассматривались три альтернативы:

1. Оставить существующий монолит.
2. Полностью переписать систему на микросервисы.
3. Выполнить постепенную декомпозицию с использованием Strangler Fig Pattern.

### Альтернатива 1. Монолит

**Плюсы:**

* минимальные изменения;
* отсутствуют затраты на миграцию.

**Минусы:**

* невозможно независимо масштабировать Auction Engine;
* сохраняется единая база данных;
* не выполняются требования по SLA;
* остаются существующие узкие места.

### Альтернатива 2. Полная микросервисная архитектура

**Плюсы:**

* независимое масштабирование;
* изоляция сервисов;
* высокая гибкость архитектуры.

**Минусы:**

* высокий риск проекта;
* значительные затраты;
* невозможно реализовать за три месяца;
* требуется построение новой инфраструктуры.

### Альтернатива 3. Strangler Fig Pattern

**Плюсы:**

* постепенная миграция;
* отсутствие остановки бизнеса;
* независимое масштабирование новых сервисов;
* возможность контролировать результаты после каждого этапа.

**Минусы:**

* временное сосуществование монолита и микросервисов;
* повышение сложности интеграции.

## Решение

В качестве стратегии развития выбрана **постепенная декомпозиция монолита по Strangler Fig Pattern**.

Приняты следующие принципы:

* в первую очередь выделяются наиболее нагруженные компоненты (Auction Service, Statistics Service, DSP Integration Service);
* новые сервисы получают собственные базы данных;
* взаимодействие между сервисами выполняется через API Gateway, REST/gRPC и Kafka;
* новые компоненты масштабируются независимо от монолита;
* миграция выполняется без остановки платформы.

## Последствия

### Положительные

* снижение риска миграции;
* достижение требуемого SLA;
* возможность независимого масштабирования;
* постепенное устранение технического долга;
* подготовка платформы к нагрузке 50 000 RPS.

### Отрицательные

* увеличение сложности архитектуры;
* необходимость сопровождения гибридной архитектуры;
* увеличение количества интеграционных взаимодействий.

### Риски

* увеличение сроков миграции при высокой связанности компонентов монолита;
* необходимость синхронизации данных между старой и новой архитектурой;
* временное увеличение эксплуатационных затрат из-за одновременной поддержки двух архитектур.
