# ADR-002. Выделение Bidding Service в качестве первого приоритета

**Дата:** 2026-08-05

**Статус:** Создано

## Контекст

В текущей архитектуре AdScale компонент **Auction Engine** является наиболее критичным элементом платформы и входит в **hot path** обработки каждого RTB-запроса. Именно он выполняет выбор победителя аукциона и определяет время ответа системы.

Сейчас Auction Engine работает внутри монолита и для каждого запроса синхронно обращается к общей базе данных PostgreSQL для получения информации о рекламных кампаниях и ставках. При пиковых нагрузках это приводит к росту времени отклика, поскольку Auction Engine конкурирует за ресурсы базы данных с сервисами статистики, финансов и аналитики.

### Ключевые архитектурные драйверы

* Производительность: P95 ≤ 100 мс
* Масштабируемость: поддержка 18 000 RPS с возможностью роста до 50 000 RPS
* Доступность: отсутствие деградации при увеличении нагрузки
* Минимизация изменений критического пути обработки RTB-запросов
* Инкрементальная миграция без остановки бизнеса
* Ограниченный бюджет и срок реализации проекта — 3 месяца

Рассматривались три альтернативы:

1. Сохранить Auction Engine внутри монолита.
2. Первым выделить другой сервис (Statistics Service или Financial Service).
3. Выделить Bidding Service как первый микросервис.

### Альтернатива 1. Оставить Auction Engine в составе монолита

**Плюсы:**

* отсутствуют затраты на миграцию;
* не требуется изменение существующей архитектуры.

**Минусы:**

* невозможно независимо масштабировать наиболее нагруженный компонент;
* сохраняются синхронные обращения к PostgreSQL в критическом пути;
* не устраняется основная причина превышения SLA;
* дальнейший рост нагрузки приводит к увеличению задержек.

### Альтернатива 2. Первым выделить другой сервис

**Плюсы:**

* снижение нагрузки на отдельные подсистемы (например, статистику или финансы);
* упрощение последующей декомпозиции монолита.

**Минусы:**

* практически не влияет на время обработки RTB-запросов;
* основные узкие места остаются в Auction Engine;
* эффект для достижения SLA минимален.

### Альтернатива 3. Выделить Bidding Service

**Плюсы:**

* независимое масштабирование наиболее нагруженного компонента;
* сокращение времени обработки RTB-запросов;
* возможность использования Redis для хранения часто используемых данных;
* снижение нагрузки на PostgreSQL;
* максимальный эффект для достижения целевых показателей производительности.

**Минусы:**

* требуется выделение бизнес-логики из монолита;
* увеличивается количество сетевых взаимодействий между сервисами;
* необходимы мониторинг и трассировка распределённых вызовов.

## Решение

Первым этапом декомпозиции монолита выделяется **Bidding Service** как самостоятельный микросервис.

При реализации принимаются следующие принципы:

* Bidding Service становится единственным компонентом, выполняющим расчёт победителя RTB-аукциона;
* взаимодействие с Bid Service осуществляется по gRPC для минимизации задержек;
* часто используемые данные о кампаниях и ставках кэшируются в Redis;
* сервис масштабируется независимо от остальных компонентов платформы;
* взаимодействие с другими сервисами выполняется через строго определённые API;
* последующая запись статистики исключается из критического пути и выполняется асинхронно.

## Последствия

### Положительные

* сокращается время обработки RTB-запросов;
* появляется возможность горизонтального масштабирования Bidding Service;
* уменьшается нагрузка на PostgreSQL;
* повышается вероятность выполнения SLA P95 ≤ 100 мс;
* создаётся основа для дальнейшей декомпозиции монолита.

### Отрицательные

* увеличивается сложность архитектуры;
* появляется необходимость сопровождения распределённого взаимодействия;
* требуется внедрение мониторинга и распределённой трассировки.

### Риски

* ошибки при переносе бизнес-логики могут привести к изменению результатов аукциона;
* эффективность кэширования зависит от актуальности данных о кампаниях и ставках;
* при недостаточной производительности Redis возможно увеличение задержек в критическом пути.
