# database-strategy

# Database Strategy

## Назначение документа

Документ описывает стратегию хранения данных для микросервисной архитектуры DSP-платформы. Для каждого сервиса выбрана собственная база данных в соответствии с паттерном **Database per Service**. Выбор СУБД основан на характере нагрузки, требованиях к согласованности данных, производительности и масштабируемости.

---

# Принцип Database per Service

В архитектуре применяется паттерн **Database per Service**, согласно которому каждый микросервис полностью владеет собственной базой данных.

Основные принципы:

- каждый сервис имеет собственную схему данных;
- отсутствует общая база данных между сервисами;
- доступ к данным осуществляется только владельцем сервиса;
- взаимодействие между сервисами происходит через REST/gRPC API и события Kafka;
- каждый сервис может использовать наиболее подходящую СУБД (Polyglot Persistence).

Такой подход уменьшает связанность компонентов и позволяет независимо развивать и масштабировать сервисы.

# Выбор баз данных


|Сервис|Тип базы данных|Обоснование|
|:---|:---|:---|
|**Bidding Service**|PostgreSQL|Обрабатывает ставки в RTB-аукционах, хранит настройки алгоритмов, журналы решений и конфигурацию. Требуются ACID-транзакции, высокая скорость записи и надежность хранения.|
|**Campaign Service**|PostgreSQL|Управляет рекламными кампаниями, бюджетами, таргетингами и креативами. Данные имеют сложные связи и требуют обеспечения ссылочной целостности.|
|**Statistics Service**|ClickHouse|Хранит поток событий (показы, клики, выигрыши аукционов, расходы). Основная нагрузка — массовая запись и аналитические запросы по большим объемам данных.|
|**Analytics Service**|ClickHouse|Формирует отчеты и аналитические панели. Выполняет сложные агрегирующие запросы по историческим данным, поэтому использует колоночную аналитическую СУБД.|
|**Finance Service**|PostgreSQL|Управляет балансами рекламодателей, списанием средств и финансовыми операциями. Для денежных транзакций необходимы строгие ACID-гарантии и надежное хранение данных.|

# Обоснование выбора

## Bidding Service

Сервис ставок работает в режиме высокой нагрузки и принимает решения в течение нескольких миллисекунд. Он хранит:

- конфигурацию алгоритмов ставок;
- журнал принятых решений;
- настройки оптимизации.

Для этих данных критична надежность хранения и транзакционная согласованность, поэтому используется PostgreSQL.

---

## Campaign Service

Сервис кампаний управляет жизненным циклом рекламных кампаний.

Основные сущности:

- рекламодатель;
- кампания;
- группа объявлений;
- креатив;
- таргетинг;
- бюджет.

Между сущностями существует большое количество связей, поэтому реляционная модель данных обеспечивает простоту сопровождения и контроль целостности.

---

## Statistics Service

Сервис статистики принимает непрерывный поток событий:

- BidRequest;
- BidResponse;
- Impression;
- Click;
- WinNotice;
- SpendEvent.

Количество записей может достигать миллионов событий в сутки.

ClickHouse выбран благодаря:

- высокой скорости записи;
- эффективному хранению временных рядов;
- высокой скорости агрегирования;
- эффективному сжатию данных.

---

## Analytics Service

Сервис аналитики использует накопленную статистику для формирования:

- BI-отчетов;
- Dashboard;
- анализа эффективности кампаний;
- расчета KPI.

Основная нагрузка состоит из сложных аналитических запросов (OLAP), поэтому используется ClickHouse.

---

## Finance Service

Сервис финансов отвечает за:

- баланс рекламодателя;
- списание бюджета;
- выставление счетов;
- финансовый журнал операций.

Любая потеря данных недопустима, поэтому используется PostgreSQL с полной поддержкой ACID-транзакций.

|Тип нагрузки|База данных|Сервисы|
|:---|:---|:---|
|OLTP|PostgreSQL|Bidding Service, Campaign Service, Finance Service|
|OLAP|ClickHouse|Statistics Service, Analytics Service|

# Polyglot Persistence

В архитектуре используется подход **Polyglot Persistence**, позволяющий выбирать СУБД в зависимости от характера нагрузки.

Преимущества данного подхода:

- оптимальная производительность для каждого типа задач;
- независимое масштабирование сервисов;
- отсутствие общей базы данных;
- снижение связанности микросервисов;
- возможность дальнейшей замены СУБД без влияния на остальные сервисы.

---

# Вывод

Для транзакционных сервисов используется PostgreSQL, обеспечивающий надежность, согласованность данных и поддержку ACID-транзакций.

Для аналитических сервисов используется ClickHouse, оптимизированный для хранения больших объемов событийных данных и выполнения высокопроизводительных аналитических запросов.

Выбранная стратегия соответствует принципам **Database per Service** и **Polyglot Persistence**, что позволяет независимо масштабировать микросервисы и использовать наиболее эффективную СУБД для каждого типа нагрузки.
