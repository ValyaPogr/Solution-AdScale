# Caching Strategy

## Назначение документа

Документ описывает стратегию кэширования данных в микросервисной архитектуре DSP-платформы. Использование Redis позволяет снизить нагрузку на базы данных, уменьшить задержки при обработке RTB-аукционов и повысить общую производительность системы.

---

# Общая стратегия

В качестве распределенного кэша используется **Redis Cluster**.

Основные задачи кэширования:

- уменьшение количества обращений к PostgreSQL;
- ускорение обработки Bid Request;
- снижение времени отклика API;
- уменьшение нагрузки на сервисы кампаний и финансов.

Redis не является источником истины (Source of Truth). Все данные хранятся в основных базах данных, а Redis используется исключительно как высокопроизводительный слой кэширования.

---

# Что кэшируется


|Данные|Сервис|Причина|
|:---|:---|:---|
|Кампании|Campaign Service|Используются практически при каждом RTB-аукционе и редко изменяются.|
|Бюджеты кампаний|Campaign Service / Finance Service|Проверяются перед размещением ставки. Быстрое чтение снижает задержку принятия решения.|
|Настройки ставок|Bidding Service|Используются алгоритмом выбора ставки и изменяются значительно реже, чем читаются.|
|Таргетинги|Campaign Service|География, устройства, браузеры и другие параметры активно используются при фильтрации кампаний.|
|Профили рекламодателей|Campaign Service|Часто запрашиваются пользовательским интерфейсом и сервисами управления.|

---

# Размещение Redis

Используется выделенный кластер Redis.

Архитектура:

- Redis Cluster;
- несколько Master-узлов;
- Replica для каждого Master;
- Sentinel (или встроенные механизмы Redis Cluster) для автоматического переключения при отказе.

Каждый микросервис обращается к Redis через собственный клиент.

Схема взаимодействия:

```
Application
      │
      ▼
 Redis Cluster
      │
      ▼
 PostgreSQL / ClickHouse
```

# TTL (Time-To-Live)


|Данные|TTL|
|:---|:---|
|Кампании|10 минут|
|Бюджеты|30 секунд|
|Настройки ставок|5 минут|
|Таргетинги|30 минут|
|Профили рекламодателей|15 минут|

TTL выбирается исходя из частоты изменения данных:

- редко изменяемые данные кэшируются дольше;
- критичные данные (например, бюджеты) имеют минимальное время жизни.

---

# Стратегия инвалидации

Используется подход **Cache Aside**.

Последовательность работы:

1. приложение обращается к Redis;
2. при наличии записи данные возвращаются из кэша;
3. при отсутствии записи данные читаются из базы данных;
4. после чтения запись помещается в Redis.

При изменении данных:

1. данные обновляются в PostgreSQL;
2. соответствующая запись удаляется из Redis;
3. при следующем обращении кэш автоматически заполняется актуальными данными.

Такой подход предотвращает использование устаревшей информации и сохраняет простоту реализации.

---

# Cache Warming

После запуска сервиса кэш предварительно заполняется наиболее востребованными данными.

В кэш загружаются:

- активные рекламные кампании;
- текущие бюджеты;
- настройки алгоритмов ставок;
- часто используемые таргетинги.

Прогрев выполняется:

- при старте приложения;
- после восстановления Redis;
- по расписанию (например, каждые несколько часов).

Это позволяет избежать резкого роста нагрузки на базы данных сразу после запуска системы.

---

# Отказоустойчивость Redis

Для обеспечения высокой доступности используются:

- Redis Cluster;
- репликация данных;
- автоматическое переключение на реплику при отказе Master;
- распределение ключей между несколькими узлами.

Если Redis недоступен:

- сервисы продолжают работу;
- данные считываются напрямую из PostgreSQL или ClickHouse;
- после восстановления Redis кэш постепенно заполняется заново.

Таким образом, отказ Redis не приводит к остановке системы, а влияет только на производительность.

---

# Итоговая стратегия


|Компонент|Решение|
|:---|:---|
|Технология|Redis Cluster|
|Стратегия|Cache Aside|
|Прогрев кэша|При старте сервиса и по расписанию|
|Инвалидация|После изменения данных|
|Репликация|Redis Replica|
|Отказоустойчивость|Redis Cluster с автоматическим переключением|

---

# Вывод

Использование Redis позволяет существенно сократить задержки при обработке RTB-аукционов и снизить нагрузку на основные базы данных. Наиболее востребованные данные (кампании, бюджеты, настройки ставок и таргетинги) обслуживаются из кэша, что обеспечивает быстрое принятие решений в процессе торгов.

Стратегия **Cache Aside**, использование TTL, своевременная инвалидация и прогрев кэша обеспечивают баланс между производительностью, актуальностью данных и отказоустойчивостью системы.
