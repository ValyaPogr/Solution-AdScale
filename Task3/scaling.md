# Database Scaling Strategy

## Назначение документа

Документ описывает стратегию масштабирования баз данных микросервисной архитектуры DSP-платформы. Для каждого сервиса определены подходы к репликации, шардированию, использованию Read Replicas и применению паттерна CQRS.

---

# Общая стратегия

Для масштабирования используются следующие подходы:

- репликация PostgreSQL по схеме Primary–Replica;
- кластер ClickHouse с репликацией и шардированием;
- горизонтальное шардирование данных для сервисов с высокой нагрузкой;
- Read Replicas для аналитических запросов;
- CQRS для разделения операций записи и чтения.

Такой подход позволяет независимо масштабировать каждый сервис в зависимости от характера нагрузки.

---

# Репликация баз данных


|Сервис|Репликация|Обоснование|
|:---|:---|:---|
|**Bidding Service**|Primary–Replica|Основная нагрузка приходится на запись. Реплика используется для чтения журналов и мониторинга без влияния на обработку ставок.|
|**Campaign Service**|Primary–Replica|Большинство операций — чтение настроек кампаний. Реплики снижают нагрузку на основную БД.|
|**Statistics Service**|Репликация ClickHouse|Высокая доступность и защита от потери событий при отказе узла.|
|**Analytics Service**|Read Replicas ClickHouse|Аналитические запросы распределяются между несколькими репликами для повышения производительности.|
|**Finance Service**|Primary–Replica (синхронная репликация)|Финансовые данные критичны. Репликация обеспечивает быстрое восстановление при отказе.|

---

# Стратегия шардирования


|Сервис|Шардирование|Ключ|
|:---|:---|:---|
|**Bidding Service**|Не требуется|Объем данных умеренный, масштабирование достигается репликацией.|
|**Campaign Service**|Не требуется|Количество кампаний значительно меньше количества событий, поэтому вертикального масштабирования достаточно.|
|**Statistics Service**|Да|`campaign_id` или временной диапазон (`event_date`). Это обеспечивает равномерное распределение событий и ускоряет агрегацию.|
|**Analytics Service**|Да|Наследует стратегию Statistics Service, используя те же ключи шардирования.|
|**Finance Service**|Не требуется|Финансовые операции требуют строгой согласованности данных, поэтому шардирование усложнило бы обеспечение транзакционной целостности.|

---

# Read Replicas

Read Replicas используются для сервисов, в которых операции чтения существенно превышают количество операций записи.

### Campaign Service

Реплики обслуживают:

- получение информации о кампаниях;
- отображение настроек;
- выборки для интерфейса рекламодателя.

### Analytics Service

Использование Read Replicas обязательно.

Основные причины:

- большое количество аналитических запросов;
- построение BI-отчетов;
- формирование дашбордов;
- отсутствие влияния аналитики на загрузку узлов записи.

### Finance Service

Реплики могут использоваться для:

- формирования финансовых отчетов;
- аудита;
- просмотра истории операций.

Все операции изменения данных выполняются только через Primary-узел.

---

# Применение CQRS

Паттерн **Command Query Responsibility Segregation (CQRS)** используется там, где нагрузка на чтение значительно превышает нагрузку на запись.


|Сервис|CQRS|Обоснование|
|:---|:---|:---|
|**Bidding Service**|Нет|Основная задача — быстрое выполнение операций записи и принятие решений в режиме реального времени.|
|**Campaign Service**|Да|Запись кампаний происходит редко, а чтение выполняется значительно чаще.|
|**Statistics Service**|Да|Потоковая запись событий отделяется от аналитических запросов.|
|**Analytics Service**|Да|Все запросы являются операциями чтения и выполняются независимо от процессов загрузки данных.|
|**Finance Service**|Частично|Финансовые операции выполняются через командную модель, а отчеты и аудит используют отдельную модель чтения.|

# Вывод

Масштабирование построено с учетом характера нагрузки каждого сервиса.

Для транзакционных сервисов (**Bidding, Campaign, Finance**) применяется репликация PostgreSQL по схеме Primary–Replica, обеспечивающая отказоустойчивость и возможность распределения операций чтения.

Для сервисов обработки больших объемов событий (**Statistics, Analytics**) используется кластер ClickHouse с репликацией и шардированием. Аналитические запросы выполняются через Read Replicas, что позволяет масштабировать чтение независимо от записи.

Паттерн CQRS применяется в сервисах, где чтение значительно преобладает над записью, что повышает производительность и упрощает горизонтальное масштабирование.
