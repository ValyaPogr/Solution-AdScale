# failover

# Data Failover Strategy

## Назначение документа

Документ описывает стратегию обеспечения отказоустойчивости данных в DSP-платформе. Рассматриваются целевые показатели восстановления (RPO и RTO), стратегия резервного копирования и соответствие принципам 12-факторных приложений.

---
# Целевые показатели восстановления

Для каждого сервиса определены допустимые значения RPO (Recovery Point Objective) и RTO (Recovery Time Objective).

- **RPO** — максимально допустимая потеря данных.
- **RTO** — максимально допустимое время восстановления работы сервиса.


|Сервис|RPO|RTO|Обоснование|
|:---|:---|:---|:---|
|**Bidding Service**|до 1 минуты|до 5 минут|Потеря части информации о ставках допустима, так как новые аукционы продолжают поступать.|
|**Campaign Service**|до 5 минут|до 15 минут|Изменения кампаний происходят относительно редко и могут быть восстановлены из резервной копии.|
|**Statistics Service**|до 10 минут|до 30 минут|Потеря небольшой части статистических данных допустима и не влияет на работу системы.|
|**Analytics Service**|до 30 минут|до 1 часа|Аналитика строится на исторических данных, поэтому небольшая задержка восстановления допустима.|
|**Finance Service**|0–1 минута|до 5 минут|Финансовые данные являются критичными и должны быть максимально защищены от потери.|

# Стратегия резервного копирования

Для хранения данных используется комбинированная стратегия резервного копирования.

## PostgreSQL

Для сервисов **Bidding Service**, **Campaign Service** и **Finance Service** выполняются:

- ежедневное полное резервное копирование;
- регулярное резервное копирование журналов транзакций;
- хранение нескольких последних резервных копий.

Это позволяет восстановить данные в случае сбоя или ошибки.

## ClickHouse

Для сервисов **Statistics Service** и **Analytics Service** выполняются:

- ежедневные резервные копии данных;
- репликация между узлами кластера;
- восстановление из резервной копии при необходимости.

Такой подход обеспечивает сохранность статистических данных и аналитической информации.

---
# Обеспечение отказоустойчивости

Для повышения надежности используются следующие решения:

- репликация баз данных;
- регулярное резервное копирование;
- использование Kafka для надежной передачи событий;
- Redis применяется только как кэш и не является основным хранилищем данных;
- автоматический перезапуск сервисов средствами контейнерной платформы.

При отказе одного из компонентов система продолжает работу, а после восстановления синхронизирует данные.

# План аварийного восстановления (Disaster Recovery Plan)

## Сценарий аварии

Возможные причины:

- отказ сервера базы данных;
- отказ узла Kafka;
- отказ Redis;
- потеря виртуальной машины;
- сбой сети.

## Переключение трафика

1. Обнаружение отказа системой мониторинга.
2. Переключение клиентов на резервный экземпляр сервиса.
3. Переключение PostgreSQL на Replica.
4. Переподключение сервисов к новой основной базе данных.
5. Возобновление обработки запросов.

## Порядок восстановления

1. Запуск нового экземпляра базы данных.
2. Восстановление данных из резервной копии (при необходимости).
3. Синхронизация с репликой.
4. Проверка работоспособности сервисов.
5. Возврат системы в штатный режим.

## Хранение резервных копий

- ежедневные полные резервные копии;
- хранение резервных копий не менее 30 дней;
- размещение копий на отдельном сервере хранения;
- регулярная проверка возможности восстановления данных.

# Соответствие принципам 12-факторных приложений

Архитектура соответствует основным принципам 12-факторных приложений.

|Принцип|Реализация|Компоненты TO-BE|
|:---|:---|:---|
|**Кодовая база (Codebase)**|Каждый микросервис имеет собственный репозиторий и управляется независимо.|API Gateway, DSP Gateway, Auction Service, Campaign Service, Delivery Service, Statistics Service, Financial Service, Analytics Service|
|**Зависимости (Dependencies)**| Зависимости каждого сервиса явно описаны и устанавливаются при сборке.|Все микросервисы (Go, C++, Python, Node.js), Docker-контейнеры|
|**Конфигурация (Config)**|Конфигурация хранится отдельно от кода и передается через переменные окружения.|Все микросервисы, Kubernetes ConfigMap/Secrets|
|**Сторонние сервисы (Backing Services)**|Базы данных, брокеры сообщений и кэш используются как подключаемые внешние сервисы.|PostgreSQL, ClickHouse, Kafka, Redis Cluster|
|**Сборка, выпуск, запуск (Build, Release, Run)**|Процессы сборки, доставки и запуска разделены.|CI/CD pipeline, Docker images, Kubernetes Deployment|
|**Процессы (Processes)**|Сервисы работают как независимые stateless-процессы и не хранят состояние внутри приложения.|API Gateway, Auction Service, Campaign Service, Statistics Service, Analytics Service|
|**Порт привязки (Port Binding)**|Каждый сервис предоставляет собственный API через определенный порт.|API Gateway, gRPC API, REST API микросервисов|
|**Конкурентность (Concurrency)**|Масштабирование выполняется запуском дополнительных экземпляров сервисов.|Kubernetes Pods, Horizontal Pod Autoscaler, Auction Service replicas|
|**Утилизируемость (Disposability)**|Сервисы могут быстро запускаться, останавливаться и восстанавливаться после сбоя.|Kubernetes, Health Checks, Auto Restart, Rolling Update|
|**Среды разработки и эксплуатации (Dev/Prod Parity)**|Среды разработки, тестирования и production используют одинаковые технологии.|Docker, Kubernetes, PostgreSQL, Kafka, Redis|
|**Логи (Logs)**|Логи собираются централизованно и анализируются через систему мониторинга.| Все микросервисы, Log Aggregator, Monitoring System|
|**Административные процессы (Admin Processes)**| Служебные операции выполняются отдельно от основных процессов приложения.|Миграции БД, Batch Jobs, Data Processing Jobs, Analytics Jobs|

# Итоговая стратегия

|Компонент|Решение|
|:---|:---|
|Репликация БД|PostgreSQL Primary–Replica, репликация ClickHouse|
|Резервное копирование|Ежедневные резервные копии|
|Потеря данных|Минимизируется за счет репликации и резервного копирования|
|Передача событий|Apache Kafka|
|Кэш|Redis (не является источником истины)|
|Конфигурация|Переменные окружения|

# Вывод

Отказоустойчивость DSP-платформы обеспечивается за счет репликации баз данных, регулярного резервного копирования и использования Kafka для передачи событий между сервисами. Выбранные значения RPO и RTO соответствуют критичности каждого сервиса: финансовые данные требуют минимальных потерь и быстрого восстановления, тогда как для статистики и аналитики допустимы более длительные сроки восстановления.

Применение принципов 12-факторных приложений способствует упрощению развертывания, масштабирования и сопровождения микросервисной архитектуры.
