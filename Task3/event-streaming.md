# event-streaming

# Event Streaming Strategy

## Назначение документа

Документ описывает архитектуру потоковой обработки событий в DSP-платформе. Для обмена сообщениями между микросервисами используется Apache Kafka. Это позволяет организовать асинхронное взаимодействие сервисов, уменьшить их связанность и обеспечить обработку большого количества событий в режиме реального времени.

---

# Общая архитектура

Apache Kafka используется как центральная шина событий между микросервисами.

Основные преимущества такого подхода:

- асинхронное взаимодействие сервисов;
- снижение связанности компонентов;
- обработка большого количества сообщений;
- возможность независимого масштабирования сервисов.

Каждый сервис публикует события в Kafka (Producer), а заинтересованные сервисы получают их (Consumer).

---

# Топики Kafka


|Топик|Producer|Consumer|Назначение|
|:---|:---|:---|:---|
|**bid-response**|Bidding Service|Statistics Service|Передача результатов расчета ставок.|
|**auction-win**|Bidding Service|Statistics Service, Finance Service|Информация о выигрыше аукциона.|
|**impression**|Ad Server|Statistics Service, Analytics Service|Регистрация показа рекламы.|
|**click**|Ad Server|Statistics Service, Analytics Service|Регистрация клика по объявлению.|
|**campaign-updated**|Campaign Service|Bidding Service, Analytics Service|Уведомление об изменении параметров кампании.|
|**budget-updated**|Finance Service|Campaign Service, Bidding Service|Обновление информации о бюджете кампании.|
|**finance-event**|Finance Service|Analytics Service|Передача финансовых операций для формирования отчетов.|

---

# Формат сообщений

Для передачи событий используется формат **JSON**.

Причины выбора:

- простота реализации;
- читаемый формат;
- поддерживается большинством языков программирования;
- подходит для учебного проекта.

Пример сообщения:

```json
{
  "auctionId": "A-123456",
  "campaignId": 101,
  "bidPrice": 1.25,
  "currency": "USD",
  "timestamp": "2026-08-05T12:00:00Z"
}
```

Каждое сообщение содержит идентификатор события, время его возникновения и необходимые бизнес-данные.

---

# Группы потребителей

Для каждого микросервиса создается собственная группа потребителей (Consumer Group).


|Consumer Group|Подписка на топики|
|:---|:---|
|**bidding-service-group**|campaign-updated, budget-updated|
|**statistics-service-group**|bid-response, auction-win, impression, click|
|**analytics-service-group**|impression, click, finance-event, campaign-updated|
|**finance-service-group**|auction-win|
|**campaign-service-group**|budget-updated|

Использование Consumer Groups позволяет распределять сообщения между несколькими экземплярами одного сервиса, повышая производительность и отказоустойчивость.

---

# Партиционирование

Для обработки большого количества сообщений топики разделяются на партиции.


|Топик|Ключ партиционирования|
|:---|:---|
|bid-response|auctionId|
|auction-win|campaignId|
|impression|campaignId|
|click|campaignId|
|campaign-updated|campaignId|
|budget-updated|campaignId|
|finance-event|advertiserId|

Использование одного ключа позволяет сохранять порядок обработки связанных сообщений.

---

# Политика хранения сообщений


|Топик|Время хранения|
|:---|:---|
|bid-response|1 день|
|auction-win|7 дней|
|impression|30 дней|
|click|30 дней|
|campaign-updated|7 дней|
|budget-updated|7 дней|
|finance-event|90 дней|

Срок хранения зависит от назначения данных:

- события аукционов хранятся недолго и используются для оперативной обработки;
- статистические данные сохраняются дольше для формирования отчетов;
- финансовые события имеют увеличенный срок хранения для проведения аудита.

---

# Надежность доставки

Для повышения надежности используются следующие механизмы:

- репликация данных между брокерами Kafka;
- автоматическое восстановление после отказа брокера;
- подтверждение получения сообщений потребителями;
- повторная обработка сообщений при временных ошибках.

Это позволяет снизить вероятность потери событий и обеспечить стабильную работу системы.

# Итоговая архитектура

Синхронный RTB-запрос проходит через API Gateway и DSP Gateway непосредственно в Bidding Service. Kafka не участвует в критическом пути обработки Bid Request.

```plaintext
                  +-------------+
                  | API Gateway |
                  +-------------+
                         |
                         | HTTP/OpenRTB
                         v
                  +-------------+
                  | DSP Gateway |
                  +-------------+
                         |
                         | gRPC
                         v
                  +---------------+
                  | Bidding       |
                  | Service       |
                  +---------------+
                         |
                         | Bid Response
                         v
                  +-------------+
                  | DSP Gateway |
                  +-------------+
                         |
                         v
                  +-------------+
                  | API Gateway |
                  +-------------+
                         |
                         v
                    DSP / SSP
```

```plaintext
              События после обработки запроса
                         |
                         v
                  +-----------+
                  |   Kafka   |
                  +-----------+
                    /    |    \
                   /     |     \
                  v      v      v
          +---------+ +---------+ +---------+
          |Statistics| |Analytics| | Finance |
          | Service  | | Service  | | Service |
          +---------+ +---------+ +---------+
```

```plaintext
Campaign Service
       |
       | campaign-updated
       v
     Kafka

Finance Service
       |
       | budget-updated
       v
     Kafka
       |
       +------------------> Bidding Service
```

# Вывод

Apache Kafka используется для организации обмена событиями между микросервисами DSP-платформы. Передача сообщений в формате JSON обеспечивает простую интеграцию сервисов, а использование топиков и групп потребителей позволяет независимо масштабировать компоненты системы.

Предложенная архитектура подходит для обработки большого количества событий в режиме реального времени и обеспечивает надежное взаимодействие между сервисами статистики, аналитики, финансов, кампаний и ставок.
