# Проектирование взаимодействия сервисов

## Общая схема взаимодействия

В архитектуре RTB используются три типа взаимодействия:

* **синхронное** — для операций, результат которых необходим немедленно;
* **асинхронное** — для событий, не влияющих на обработку текущего запроса;
* **внешнее HTTP-взаимодействие** — для интеграции с DSP.

Соответствие типов взаимодействия приведено в таблице.


|Взаимодействие|Протокол|Причина выбора|
|:---|:---|:---|
|DSP → API Gateway → Bidding Service|HTTPS (REST)|Совместимость с внешними DSP|
|Bidding → Campaign Service|gRPC|Минимальная задержка|
|Bidding → Budget Service|gRPC|Быстрая синхронная проверка бюджета|
|Bidding → Targeting Service|gRPC|Проверка таргетинга в реальном времени|
|Campaign → Kafka|Kafka|Распространение изменений кампаний|
|Click/Impression → Kafka|Kafka|Высокая скорость обработки событий|
|Analytics ← Kafka|Kafka|Независимое масштабирование аналитики|

# Выбор протоколов

## REST для внешней интеграции с DSP

Большинство DSP взаимодействуют по HTTP(S) с использованием JSON. Поэтому внешнее API строится на REST.

**Преимущества:**

* совместимость с большинством DSP;
* простота интеграции;
* использование стандартных HTTP-механизмов (TLS, заголовки, коды ответов);
* отсутствие необходимости поддерживать специализированные клиенты.

Недостатком REST являются более высокие накладные расходы по сравнению с gRPC, однако это компенсируется требованием совместимости с внешними системами.

---

## gRPC для внутренних сервисов

Внутреннее взаимодействие между Bidding Service и сервисами Campaign, Budget и Targeting реализуется через gRPC.

Причины выбора:

* бинарная сериализация Protocol Buffers уменьшает объём передаваемых данных;
* HTTP/2 поддерживает мультиплексирование запросов;
* ниже задержка по сравнению с REST;
* меньше потребление CPU и сетевых ресурсов;
* строго типизированные контракты упрощают сопровождение API.

Поскольку расчёт ставки выполняется в пределах **100 мс**, уменьшение задержек внутренних вызовов критично для соблюдения SLA.

---

## Почему не REST между Bidding и Campaign?

REST подходит для CRUD-операций и интеграции между независимыми системами, однако в RTB каждое обращение находится на критическом пути обработки запроса.

Использование REST привело бы к:

* увеличению размера сообщений (JSON);
* дополнительным затратам на сериализацию;
* большей задержке обработки.

Поэтому для внутренних вызовов выбран **gRPC**.

# Использование Kafka

Kafka применяется только для передачи событий.

Основные события:

* BidCreated;
* ImpressionCreated;
* ClickCreated;
* CampaignUpdated;
* BudgetUpdated.

События публикуются после завершения обработки запроса и не блокируют ответ DSP.

---

## Почему Kafka

Kafka обеспечивает:

* высокую пропускную способность;
* асинхронную обработку;
* возможность подключения нескольких потребителей;
* повторное чтение событий;
* горизонтальное масштабирование.

Kafka хорошо подходит для потоков кликов и показов, поскольку такие события поступают непрерывно и не требуют мгновенного ответа отправителю.

# Паттерны взаимодействия

## Синхронный Request–Response

Используется для:

* расчёта ставки;
* проверки бюджета;
* проверки таргетинга.

```
DSP
   │
HTTP
   │
API Gateway
   │
gRPC
   │
Bidding
 ├────────► Campaign
 ├────────► Budget
 └────────► Targeting
```

---

## Асинхронный Publish–Subscribe

Используется для передачи событий.

```
Bidding
   │
Publish
   │
Kafka
 ├────────► Analytics
 ├────────► Reporting
 ├────────► ML
 └────────► Monitoring
```

---

# API Gateway

Для интеграции с DSP используется API Gateway.

Он выполняет следующие функции:

* маршрутизация запросов;
* аутентификация;
* ограничение частоты запросов (Rate Limiting);
* балансировка нагрузки;
* мониторинг времени ответа;
* централизованное логирование;
* применение Circuit Breaker.

Использование API Gateway позволяет скрыть внутреннюю структуру микросервисов и обеспечить единую точку входа для всех DSP.

# Итоги выбора технологий


|Компонент|Выбранная технология|Обоснование|
|:---|:---|:---|
|Внешняя интеграция с DSP|REST/HTTPS|Стандарт де-факто для RTB и совместимость с внешними системами|
|Внутреннее взаимодействие Bidding ↔ Campaign/Budget/Targeting|gRPC|Минимальные задержки, бинарная сериализация, HTTP/2, высокая производительность|
|Передача событий|Kafka|Асинхронная обработка, высокая пропускная способность, независимое масштабирование потребителей|
|API Gateway|Да|Единая точка входа, маршрутизация, безопасность, Rate Limiting, балансировка, Circuit Breaker и мониторинг|

Такое разделение соответствует требованиям проекта: критический путь обработки ставок остаётся максимально быстрым благодаря **gRPC**, интеграция с внешними DSP обеспечивается через совместимый **REST/HTTPS**, а высокочастотные события кликов и показов обрабатываются асинхронно через **Kafka**, не увеличивая время ответа на запрос ставки.
