# Bidding Service

## Назначение

**Bidding Service** — высоконагруженный RTB-сервис, отвечающий за обработку запросов на участие в аукционе (Bid Request), выбор подходящей рекламной кампании и формирование ответа (Bid Response) для DSP.

Сервис выделяется из монолита как отдельный микросервис, поскольку:

* является наиболее критичным по задержкам;
* должен независимо масштабироваться;
* обрабатывает до **18 000 RPS**;
* должен обеспечивать **P95 ≤ 100 мс**;
* имеет собственную предметную область — **расчёт ставки**.

---

# Границы сервиса

## Ответственность

Bidding Service выполняет следующие функции:

* приём Bid Request;
* валидация запроса;
* поиск подходящих рекламных кампаний;
* проверка бюджета кампании;
* проверка соответствия правилам таргетинга;
* расчёт итоговой ставки;
* выбор победителя;
* формирование Bid Response;
* публикация события о результате аукциона.

---

## Не входит в ответственность

Следующие функции остаются в других сервисах:

* создание и редактирование рекламных кампаний;
* управление бюджетами;
* управление пользователями;
* хранение статистики;
* аналитика;
* финансовые операции;
* обучение ML-моделей.

# API сервиса

## POST /v1/bids

### Назначение

Обработка запроса DSP и расчёт ставки.

### Request

```json
{
  "requestId": "bid-123",
  "placementId": "banner-top",
  "floorPrice": 0.75,
  "device": {
    "os": "Android",
    "country": "RU"
  },
  "user": {
    "id": "user-100"
  }
}
```

---

### Response

```json
{
  "requestId": "bid-123",
  "campaignId": "cmp-15",
  "creativeId": "creative-42",
  "bidPrice": 1.08,
  "currency": "USD",
  "ttl": 120
}
```

---

### Если подходящей кампании нет

```
HTTP 204 No Content
```

```protobuf

    placementId,

    os
)
```

Возвращает список активных кампаний, удовлетворяющих базовым условиям.

```protobuf

```

Возвращает:

```protobuf
CheckTargeting(
    campaignId,
    user
)
```

# Модель данных

Bidding Service является **stateless-сервисом**. Постоянное хранение бизнес-данных выполняют специализированные сервисы. Сам сервис использует минимальный набор данных для трассировки и диагностики.

## BidRequest


|Поле|Тип|Назначение|
|:---|:---|:---|
|requestId|UUID|Идентификатор запроса|
|dspId|UUID|Идентификатор DSP|
|placementId|UUID|Рекламная площадка|
|floorPrice|Decimal|Минимальная ставка|
|requestTime|Timestamp|Время получения|

---

## BidResult


|Поле|Тип|Назначение|
|:---|:---|:---|
|requestId|UUID|Идентификатор запроса|
|campaignId|UUID|Выбранная кампания|
|creativeId|UUID|Креатив|
|bidPrice|Decimal|Размер ставки|
|status|Enum|WIN / NO_BID / ERROR|
|responseTimeMs|Integer|Время обработки|

---

# Использование Redis

Для сокращения времени отклика в Redis кэшируются:

* активные кампании;
* коэффициенты ставок;
* правила таргетинга;
* справочники площадок.

Обновление кэша выполняется по событиям изменения кампаний.

---

# Публикуемые события

После завершения обработки запроса публикуется событие в Kafka.

**Топик**

```
bid-events
```

**Сообщение**

```json
{
  "requestId": "bid-123",
  "campaignId": "cmp-15",
  "bidPrice": 1.08,
  "timestamp": "2026-03-15T12:15:33Z"
}
```

События используются сервисами аналитики, отчётности, мониторинга и обучения ML-моделей.

# Обоснование архитектурных решений

* **Выделение Bidding Service** соответствует принципам DDD: сервис реализует отдельный ограниченный контекст (Bounded Context) — расчёт ставок в RTB-аукционе.
* **gRPC** выбран для внутренних синхронных вызовов к Campaign, Budget и Targeting Service благодаря высокой производительности, бинарной сериализации Protocol Buffers и низким накладным расходам.
* **Kafka** используется для асинхронной передачи событий аукциона, что исключает влияние аналитических процессов на критический путь обработки ставок.
* **Redis** обеспечивает быстрый доступ к редко изменяющимся данным, уменьшая количество сетевых обращений к другим сервисам.
* **Stateless-подход** позволяет независимо масштабировать экземпляры сервиса за балансировщиком нагрузки и поддерживать требуемую производительность при высокой нагрузке.
