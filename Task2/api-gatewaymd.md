# API Gateway для интеграции с DSP

## Назначение

API Gateway является единой точкой входа для внешних DSP-площадок и обеспечивает безопасную, масштабируемую и отказоустойчивую обработку запросов на участие в RTB-аукционах.

Основные задачи API Gateway:

* приём запросов от DSP;
* маршрутизация запросов в Bidding Service;
* аутентификация клиентов;
* ограничение частоты запросов (Rate Limiting);
* балансировка нагрузки;
* применение паттерна Circuit Breaker;
* мониторинг производительности;
* централизованное логирование.

---

# Архитектура

```text
                DSP Platform
                     │
                HTTPS (REST)
                     │
              API Gateway Cluster
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
 Gateway #1    Gateway #2    Gateway #N
        │            │            │
        └────────────┼────────────┘
                     │
               Load Balancer
                     │
             Bidding Service
```

API Gateway разворачивается в нескольких экземплярах и работает без хранения состояния (**Stateless**), что позволяет горизонтально масштабировать его при увеличении нагрузки.

---

# Маршрутизация запросов

Все внешние запросы поступают через единый REST API.


|Метод|URI|Назначение|
|:---|:---|:---|
|POST|`/v1/bids`|Запрос на расчёт ставки|
|GET|`/health`|Проверка доступности сервиса|
|GET|`/metrics`|Метрики Prometheus|

После проверки запроса API Gateway перенаправляет его в **Bidding Service** по внутреннему gRPC-интерфейсу.

---

# Аутентификация

Каждая DSP получает уникальные учётные данные.

При поступлении запроса API Gateway выполняет:

* проверку API Key или OAuth 2.0 Bearer Token;
* проверку срока действия токена;
* проверку полномочий клиента;
* журналирование результата аутентификации.

При неуспешной проверке возвращается ответ:

```http
401 Unauthorized
```

---

# Ограничение частоты запросов (Rate Limiting)

Чтобы защитить систему от перегрузки и некорректного поведения клиентов, применяется ограничение частоты запросов.

Для каждой DSP настраиваются индивидуальные лимиты.

Пример:


|DSP|Ограничение|
|:---|:---|
| DSP-1|5 000 RPS|
| DSP-2|3 000 RPS|
| DSP-3|10 000 RPS|

При превышении лимита API Gateway возвращает:

```http
429 Too Many Requests
```

Такой механизм предотвращает деградацию производительности всей платформы.

---

# Circuit Breaker

Для защиты системы используется паттерн **Circuit Breaker**.

API Gateway отслеживает ошибки при обращении к Bidding Service.

### Closed

Запросы проходят в обычном режиме.

↓

### Open

При превышении заданного порога ошибок новые запросы временно не передаются в сервис.

Клиент сразу получает ответ об ошибке или резервное значение.

↓

### Half-Open

Через заданный интервал выполняется несколько тестовых запросов.

Если сервис восстановился — шлюз возвращается в состояние **Closed**.

---

# Балансировка нагрузки

API Gateway распределяет входящий поток между экземплярами Bidding Service.

Используется алгоритм:

* Round Robin;
* либо Least Connections.

При увеличении количества экземпляров дополнительная настройка клиентов DSP не требуется.

---

# Мониторинг

API Gateway собирает следующие метрики.


|Метрика|Назначение|
|:---|:---|
|RPS|количество запросов|
|P95 Response Time|время ответа|
|Error Rate|процент ошибок|
|HTTP 4xx|ошибки клиента|
|HTTP 5xx|ошибки сервера|
|Circuit Breaker State|состояние автоматического размыкателя|
|Active Connections|активные соединения|

Метрики экспортируются в Prometheus и используются Grafana для построения дашбордов и настройки оповещений.

---

# Логирование

Для каждого запроса сохраняются:

* Request ID;
* DSP ID;
* время получения запроса;
* время обработки;
* HTTP-статус;
* код ошибки (при наличии);
* IP-адрес клиента.

Логи используются для диагностики, аудита и анализа производительности.

---

# Отказоустойчивость

При недоступности Bidding Service API Gateway выполняет следующие действия:

1. активирует Circuit Breaker;
2. прекращает отправку новых запросов в недоступный экземпляр;
3. перенаправляет запросы на работающие экземпляры;
4. если все экземпляры недоступны — возвращает клиенту код:

```http
503 Service Unavailable
```

После восстановления сервиса выполняется автоматический возврат к штатному режиму работы.

---

# Выбор API Gateway

Для архитектуры AdScale рекомендуется использовать **Envoy Proxy**.

### Причины выбора

* высокая производительность и низкие задержки;
* встроенная поддержка HTTP/2 и gRPC;
* эффективная балансировка нагрузки;
* встроенные механизмы Circuit Breaker и Retry;
* поддержка Rate Limiting;
* интеграция с Prometheus и Grafana;
* возможность динамической конфигурации без перезапуска.

## Обоснование архитектурного решения

Использование API Gateway позволяет изолировать внутреннюю архитектуру платформы от внешних DSP, обеспечивая единую точку входа, централизованную аутентификацию и защиту от перегрузок. Выбор **Envoy Proxy** обусловлен его высокой производительностью, поддержкой **HTTP/2** и **gRPC**, а также встроенными механизмами балансировки нагрузки, Circuit Breaker, Rate Limiting и мониторинга. Такое решение соответствует требованиям проекта по высокой доступности, масштабируемости и соблюдению SLA с временем отклика **P95 ≤ 100 мс**.
