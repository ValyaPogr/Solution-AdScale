# reliability.md

# Паттерны надёжности

## Назначение

RTB-платформа должна обеспечивать стабильную работу при высокой нагрузке и частичных отказах компонентов. Для этого применяются архитектурные паттерны, позволяющие предотвратить каскадные сбои, сократить время восстановления и сохранить работоспособность системы.

В архитектуре используются следующие механизмы:

* Circuit Breaker;
* Retry с экспоненциальной задержкой;
* идемпотентность операций;
* резервные стратегии (Fallback).

---

# Circuit Breaker

## Назначение

Bidding Service обращается к нескольким зависимым сервисам:

* Campaign Service;
* Budget Service;
* Targeting Service.

Если один из них становится недоступен, повторные вызовы могут привести к накоплению ожидающих запросов и распространению отказа на всю систему.

Для предотвращения этого применяется паттерн **Circuit Breaker**.

---

## Состояния Circuit Breaker

### Closed

Все запросы проходят к зависимому сервису.

Если количество ошибок превышает заданный порог, происходит переход в состояние **Open**.

---

### Open

Новые запросы к недоступному сервису временно не выполняются.

Вместо ожидания ответа используется резервная стратегия (Fallback) либо клиенту возвращается ошибка.

Через заданный интервал выполняется проверка доступности сервиса.

---

### Half-Open

Выполняется ограниченное число тестовых запросов.

Если сервис отвечает корректно, Circuit Breaker возвращается в состояние **Closed**.

При повторном возникновении ошибок состояние снова меняется на **Open**.

---

## Применение


|Вызов|Circuit Breaker|
|:---|:---|
|Bidding → Campaign|Да|
|Bidding → Budget|Да|
|Bidding → Targeting|Да|
|API Gateway → Bidding|Да|

---

# Retry с экспоненциальной задержкой

Кратковременные сетевые сбои или перегрузка сервисов могут приводить к временным ошибкам. Для их обработки используются повторные попытки с увеличивающимся интервалом между ними.

Пример последовательности:


|Попытка|Задержка|
|:---|---:|
|1|100 мс|
|2|200 мс|
|3|400 мс|

Количество повторов ограничивается (например, тремя попытками), чтобы избежать дополнительной нагрузки на сервис.

**Retry применяется только для временных ошибок** (например, тайм-аутов или кратковременной недоступности) и не используется при ошибках валидации или некорректных запросах.

---

# Идемпотентность операций

Финансовые операции не должны выполняться повторно при повторной отправке одного и того же запроса.

Для этого каждый запрос получает уникальный идентификатор (**Request ID**), который сохраняется и проверяется при повторном поступлении.

## Пример

Первый запрос:

```text
Request ID = bid-123
```

Если тот же запрос поступит повторно:

```text
Request ID = bid-123
```

система распознает дубликат и не выполнит повторное списание бюджета или повторную регистрацию операции.

Такой подход исключает двойную обработку при повторной доставке сообщений или повторных запросах клиента.

---

# Резервные стратегии (Fallback)

Если зависимый сервис временно недоступен, используются резервные сценарии обработки.

## Использование кэша

При недоступности Campaign Service или Targeting Service Bidding Service может использовать данные из Redis:

* активные кампании;
* правила таргетинга;
* коэффициенты ставок.

Это позволяет продолжить обработку запроса без обращения к недоступному сервису.

---

## Дефолтная ставка

Если невозможно вычислить оптимальную ставку, система может вернуть заранее определённое безопасное значение.

Например:

```text
Default Bid = Floor Price
```

Такой подход позволяет сохранить участие в аукционе даже при частичной недоступности инфраструктуры.

---

## Отказ от участия в аукционе

Если расчёт ставки невозможен и резервные стратегии неприменимы, система возвращает ответ **No Bid** без формирования некорректной ставки.

Это предотвращает финансовые риски и обеспечивает корректное поведение платформы.

---

# Мониторинг надёжности

Для контроля состояния системы собираются следующие показатели.


|Метрика|Назначение|
|:---|:---|
|Error Rate|Доля ошибочных запросов|
|Retry Count|Количество повторных попыток|
|Circuit Breaker State|Состояние автоматического размыкателя|
|Fallback Usage|Частота использования резервных стратегий|
|Service Availability|Доступность сервисов|
|P95 Response Time|Время отклика|

Метрики передаются в систему мониторинга и используются для настройки оповещений и анализа стабильности платформы.

# Итоговая схема

```text
                  API Gateway
                       │
                       ▼
               Bidding Service
        ┌─────────┼─────────┐
        ▼         ▼         ▼
   Campaign   Budget   Targeting
    Service   Service    Service
        │         │         │
        └──────┬──┴─────────┘
               ▼
        Circuit Breaker
               │
     ┌─────────┴──────────┐
     ▼                    ▼
 Retry (Backoff)      Fallback
                           │
                   Redis / Default Bid
```

# Обоснование архитектурных решений

* **Circuit Breaker** предотвращает каскадные отказы, временно прекращая обращения к недоступным сервисам и позволяя им восстановиться без дополнительной нагрузки.
* **Retry с экспоненциальной задержкой** помогает устранить влияние кратковременных сетевых сбоев, не создавая лавинообразного увеличения числа запросов.
* **Идемпотентность** гарантирует, что повторная обработка одного и того же запроса не приведёт к повторному резервированию бюджета или другим финансовым ошибкам.
* **Fallback-стратегии** (использование кэша Redis, возврат безопасной ставки или ответа **No Bid**) позволяют сохранить работоспособность системы даже при частичной недоступности зависимых сервисов и обеспечивают выполнение требований по высокой доступности и времени отклика.
